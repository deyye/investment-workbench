## 删除与一键清空、侧栏项目卡片化（2026-09-14）

- 删除从「界面改不了」变成「可恢复」。此前没有任何删除入口，只能进 `data/` 手删文件——而**人工核对成果（修订值、证据绑定、修订历史）只存在该文档的 json 里**，手删等于把核对工作一并丢掉。现在删除**只做移入回收站**（`data/.trash/<时间戳>-<id>/`），彻底删除是回收站内的独立动作，另需 `PURGE` 口令。
- 新增接口：`POST /api/documents/delete`（覆盖单份／整个项目／全部三种粒度）、`GET /api/trash`、`POST /api/trash/restore`、`POST /api/trash/purge`。
- 修复清单（均为本轮实现过程中暴露）：
  - 清空口令原先按「待删 id 是否覆盖全部文档」判定，导致**只有一个项目时删除该项目被误判成清空**而卡住。改为按请求里的 `scope` 判定意图，并要求 ids 与当前集合严格相等；口令带份数，兼作**范围漂移守卫**（界面渲染之后又有文件传入会被拒绝，而不是多删）。
  - 恢复时原编号被占用，第一版命名成 `<旧编号>.restored-xxxx.json`，**破坏了 `get()` 强制的 32 位十六进制编号规则**，恢复出来的文档将无法读取——比直接失败更糟。改为分配新编号并同步改写 json 内的 `id`。

## 发文字号书写形态与企业投资项目阶段归类（2026-09-14）

两处都是先查证、后动手，改动本身不大，但都对应「输出看起来正常、其实是错的」这一类静默问题。

### 发文字号：括号必须放宽，且 OCR 读不出六角括号

- 国标 GB/T 9704-2012 §7.2.5 规定发文字号年份用**六角括号「〔〕」**括入、数字用半角阿拉伯数字。所谓「全角／半角」的问法需要澄清：规范形态既不是全角方括号也不是半角方括号。
- 但现实里至少三种变形会出现：源 PDF 文本层直接写成半角「[]」（实测一份可研批文即如此，逐格核对证据行，`值 == 原文`，确认不是抽取改的）；部分发布系统输出全角方头括号「【】」；版头为图片层时只能靠 OCR。
- **实测 macOS Vision 读不出六角括号**：自造图片经 `app/macos_vision_ocr.js` 识别，`〔2025〕` 在宋体下变成 `［2025］`、冬青黑下变成 `（2025）`；按 300dpi 字号复测，**公文 3 号字（16pt，正是发文字号的实际字号）下读成 `【2025〕`（左右括号只错一个）**，24pt 以上才读对。即错误形态随字体／字号／DPI 变化，落点不可预测。
- 原正则 `[〔\[]…[〕\]]` 只认半角与六角，上述形态**全部失配**。而这行正则被**三处复用**：`header_band()` 定位版头带底边、字段抽取、以及定位主送机关（项目单位）的起点。失配的代价不只是字段为空，还连带打坏另外两处的锚点。
- 修复：括号类放宽到 `〔 [ ［ 【 （ (` × `〕 ] ］ 】 ） )`；判定仍靠 `fullmatch` 要求整行是「代字＋括号年份＋序号＋号」的完整形态，故正文里的「（2026）」不会被误认成文号。
- **主字段一律留原文**——文号要拿去和纸质件、平台数据核对，改写原始写法会掩盖来源本身的问题（是文件写错了，还是我们认错了）。另在 cell 上挂 `normalized`（括号折成〔〕、全角数字转半角、去空白）**只供机器判断「是否同一文号」**；写法不符国标时追加一句提示，原文不动。
- 实测：47 份语料**全部本来就是六角括号**（与国标一致），故新增的「写法不符」提示在语料上触发 0 次；规则改动的收益在**将来走 OCR 的批文**上，属预防性修复。已用合成材料端到端验证半角形态：原文保留 `瑞发改投[2026]55号`、归一化值 `瑞发改投〔2026〕55号`、提示照常给出。

### 阶段归类：核准/备案单独成类，不再落入「待确认」

- 「核准」与「审批」是两条轨道：政府投资项目走**审批**（项目建议书→可研→初设三关），企业投资项目走**核准／备案**，没有这三关。原先一律归入「待确认」，把「不属于这个体系」和「判定不出来」混为一谈，而这两者处置相反：前者照原样归档即可，后者必须人工介入。
- 实测 47 份语料：25 份初设、14 份可研、5 份建议书-立项，其余 **3 份标题全是「…项目核准的批复」**（天然气门站、中压燃气）。新增「核准/备案」后这 3 份各得其所，`待确认` 归零。
- 判定抽成 `classify_stage(title)` 独立函数（原先内联在 `extract()` 里），顺序为 核准/备案 → 初步设计 → 可行性研究 → 建议书/立项 → 待确认。同时确认**「立项」与「建议书」指同一审批事项**（庆元写「项目建议书的批复」、龙泉写「立项申请的批复」），必须归到同一档，否则同一项目的三份批文跨阶段对不上。
- 联动修复：
  - `compare.py` 的阶段排序兜底下标由写死的 `3` 改为 `len(STAGES)-1`。写死的数字在原表下恰好等于「待确认」位次，一旦增删阶段就会把未知阶段排到已知阶段中间。
  - `queue.py` 的待办生成：`核准/备案` 是已定论的归类（标题明写），不再占用人工待办；`待确认` 仍然生成。
  - 侧栏胶囊：三个阶段占位原先无条件显示，导致核准项目挂三个「未上传」、**等于谎报缺失**（而该项目本来就没有这三关）。现改为只在项目确实含三阶段批文时才显示这三个占位，实际出现过的阶段一律补上。
  - 前端阶段短名表补 `核准/备案 → 核准`；阶段下拉框与人工确认由 `STAGES` 自动带出，无需另改。
